# 实施路线与验收

版本：0.1 / 提案。按依赖推进，不承诺未经估算的日历日期。

## 1. 推进原则

先证明“值得玩的一小段”，再扩为完整内容。每个阶段有明确交付物和退出条件；失败时修该层，不用更多页面或素材掩盖。

用户要求先完成策划，再推进 UI 和程序。本目录先成为工作依据；本轮被否决的网页视觉不继续扩展，新概念图保持候选状态。

## 2. 阶段路线

| 阶段 | 核心问题 | 交付物 | 进入下一阶段的条件 |
| --- | --- | --- | --- |
| P0 策划基线 | 游戏为什么值得回来？规则是否自洽？ | 总策划、数值、UI/美术、架构、决策、固定演示脚本、审查记录 | 规则冲突有明确处置；每个核心系统有输入、产出、边界和验收 |
| P1-A 同屏美术与交互样板 | 看上去是不是精致像素游戏？ | 一间房间、两阶段机台、角色/伙伴、一个游戏对话框、手册入口的同屏样板 | 用户认可游戏质感；无网页面板；统一视角、像素尺度与文字 |
| P1-B 可玩成长切片 | 收获、成长、拿奖、摆放能否形成一次想再玩的体验？ | 固定三次演示输入、一次机台进化、一次伙伴进化、植物/猫等代表礼物、一次扭蛋、一次摆放、刷新保留 | 无口头指导完成循环；看得见奖励用途；核心交易和存档测试通过 |
| P2 完整 V2 | 系统能否支持长期个人表达？ | 五阶段机台、四形态伙伴动作、七章、50 件库存兼容、主题/相框、全部游戏 UI、愿望、确定货架 | 每个开启入口有完整状态；桌面关键流程与小屏目标通过；老存档兼容 |
| P3 内容扩展 | 能否低成本添内容而不重做系统？ | 第一册新主题内容 / 新场景试点 | 主要通过内容配置与资产接入；旧完成纪念和布局不丢 |

P1-A 的用户视觉认可是一道质量门槛，不是默认把未评价的生成图算认可。不会在收到“太像网页”后继续铺满其余屏幕。

## 3. P1 的具体范围

### 必做

- 主房间构图与统一美术样板；底层动作可先简化，视觉不拿网页占位宣称完成。
- 至少 1 台项目机台能从白银到蓝；4 个近景机位与超出访问规则验证。
- 店长可移动；小光幼体/第二阶段、一次点击回应与跟随动作。
- 前三章礼物达到、领取、重复补偿、用途说明与摆放闭环。
- 一次扭蛋有完整操作与结果，跳过/刷新不丢奖。
- **P1-B 前置修复**：已结算高水位、异步同步跨模式、命令事务与存储失败状态机；旧档兼容、真实/演示隔离、同一章节不可重领。不能延后到 P2。
- 关键入口能由鼠标、键盘、触摸等效触发。
- 所有演示状态明示虚构，首次无历史仍需主动选择。

### 不夹带进入 P1

新货币、伙伴饥饿、复杂 NPC 经营、多房间、皮肤商店、限时主题、任务面板、全量资源一次性生成、引擎大迁移。

现有 50 件收藏在数据层保留；艺术上优先精修 `c_sprout`、`c_mug`、`r_cat`、`c_gg`、`r_frame`、`e_sunset` 六件样品，不因为先做样板删除其他库存。

## 4. 可试玩切片的逐步验收脚本

| 步骤 | 玩家动作 | 必须观察到 | 数据检查 |
| --- | --- | --- | --- |
| 1 | 首次打开 | 能辨认小屋、伙伴、储蓄罐 | 无真实记录时不自动发虚构币 |
| 2 | 主动进入演示 | 模式标识明确，简单开场 | 独立 demo 槽 |
| 2a | 0 token / 0 收藏切换免费基础布局 | 木凳、灯、绿植换到新锚点，重开保持 | starterPresetId 保存；币和收藏数量不变 |
| 3 | 第一次演示收获 | 机台通电、币进入计数器、手册可领奖 | 10K 合法输入，≥1 币 |
| 4 | 领植物、摆上地台 | 奖品是主场景里的物件 | chapterId 已领取、owned、layout 合法 |
| 5 | 重复点击/重开 | 不重复得到植物 | 钱包与领取记录不变 |
| 6 | 第二次演示收获 | 蓝机台和伙伴进化 | 累计 100K，阶段一致 |
| 7 | 第三次演示收获、领猫，再抽奖 | 演示首奖 c_gg，完成墙面摆放 | cozy-intro-v1 / mulberry32(22)，累计 250K，单抽正好扣 25 |
| 8 | 设心爱机台、调整摆设 | 房间表现实际变化 | 选择与布局落盘 |
| 9 | 刷新或关闭重开 | 回到刚才自己的小屋 | 钱包、奖励、主题、布局相符 |
| 10 | 相同真实汇总重放/零新增 | 平静告知无新收获 | 不铸币、不重领奖 |

测试不能在点击失败后通过 `store.pull()` / `store.claimGrowth()` 补动作，再宣称 UI 通过。单元测试可以直接调用领域方法；浏览器验收必须真正操作目标入口。

## 5. 后续 P2 分块顺序

1. 在 P1-B 已修复并通过的交易/迁移边界上扩大数据来源和异常 fixture 覆盖；已知重复结算与跨槽问题不能遗留到此时。
2. 完整机台近景、五阶段图鉴、心爱机台和长名称处理。
3. 四阶段伙伴的完整动作与已解锁外形选择。
4. 七章完整手册、批量领取、单愿望状态。
5. 收藏册、确定货架、重复/星尘文案与实际目录一致。
6. 装饰、主题、相框同场景兼容；完善移动视窗和读屏/键盘流程。
7. 全流程视觉 QA、性能检查、干净/旧存档回归、打包资源检查。

## 6. 风险与处置

| 风险 | 早期如何识别 | 处置 |
| --- | --- | --- |
| 还是像网页 | 无文字截图 + 实际屏幕评审 | 退回 P1-A，停止扩其他页面 |
| 只有“再抽一次”动机 | 演示后问下次期待什么 | 强化确定礼物、进化预览和奖品可用性，先不加新系统 |
| 低用量很久无变化 | 8K/10K/100K 输入样本 | 免费交互、早期礼物；不伪造收入 |
| 大历史快速毕业 | 50M/500M 模拟 | 快速结算、批量操作、永久纪念；承认内容有限 |
| 生成素材不成体系 | 混合同屏看轮廓、脚底和像素密度 | 把生成图退回概念层，统一规范后再加工 |
| 数据与动画耦合 | 揭晓中刷新、切页 | 先提交状态，动画读结果 |
| 双标签重复发奖 | 同时领奖/抽奖 | 命令串行与跨标签锁；不支持锁时只读，保存失败按恢复状态机处理 |
| 新字段使旧存档损坏 | 真实结构 fixture 迁移 | 备份、校验、幂等迁移，不清空原记录 |
| 扩展分母让玩家失去毕业 | 目录从 50 增加到 60 | 固定主题册 ID 集合与完成纪念 |

## 7. 完成定义

“策划完成”只表示文档和审查覆盖到位，不代表用户已认可所有取舍。

“美术样板通过”需要用户认可像素游戏质感，不以程序截图存在代替。

“切片完成”需要上述交互、规则、持久化和视觉门槛同时满足。

“V2 完成”需要全部开放功能可用，没有沿用被否决的网页页面作为正式入口；外观、数值和叙事来自这套一致规则。
