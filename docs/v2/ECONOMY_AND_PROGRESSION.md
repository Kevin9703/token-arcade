# 数值、奖励与体验节奏

版本：0.1 / 提案。目标：确定近期反馈，保持长期成长，尊重已有历史，不鼓励无意义地消耗 token。

## 1. 唯一输入与数值职责

| 数值 | 来源 | 用途 | 会被消耗吗 |
| --- | --- | --- | --- |
| 项目累计 token | 对应项目的合法用量 | 机台等级、阶段、未来铸币倍率 | 否 |
| 全局累计 token | 所有项目的有效累计值 | 章节、小光进化 | 否 |
| 金币 | 新发现 token 的一次性结算 | 扭蛋、礼物兑换 | 是 |
| 星尘 | 已拥有物的重复获得 | 一个简单的未拥有物兑换入口 | 是 |
| 收藏拥有状态 | 抽奖、兑换、章节领取 | 陈列、装备、收藏里程碑 | 否 |
| 店长等级 | 历史累计铸币，现有公式 | 个人身份纪念，不再多加一套能力成长 | 否 |

旧存档中的 tickets 保留兼容，但在首版主 HUD 隐藏，不新设计票券经济。不能因存档中有字段就必须在玩法里赋予新职责。

机台、章节、伙伴共用同一份 token 进度；不会分别扣三次“经验”。手动交互、布置、现实日期不提供成长资源。

### 首版不额外加抽奖保底

先靠永久章节礼物和已有星尘兑换保证确定进展。新增保底会引入跨奖池计数、概率解释和旧存档迁移，须在重复体验测试后另立规则。不能暗中给“第一抽必出稀有”而仍把普通概率当作真实概率显示。

## 3. 铸币与重复结算

设项目在此次同步前的有效等级为 `L`：

```text
倍率 m(L) = 1 + ((clamp(L, 1, 50) - 1) / 49) × 0.5
本次可计奖新增量 delta = 未被结算过的合法 token
有效铸币量 = Σ(delta_project × m(level_before_sync))
池 = 上次有效 token 余量 + 本次有效铸币量
新增金币 = floor(池 / 10,000)
新余量 = 池 - 新增金币 × 10,000
```

全局和项目成长使用原始 token，不使用乘倍率后的有效铸币量。新项目首次结算按 1.00×。同一次导入跨越若干级，不把整笔旧 token 按新等级倍率重新结算。

### 例子

- Lv.1 项目导入 8,000 token：0 币，余量 8,000，项目升至 Lv.2。
- 同一报告再同步：0 币，余量不变，不多领章节。
- 全新另一个 Lv.1 项目导入 4,000：得到 1 币，合计余量 2,000。
- 花掉金币不会降低累计铸币和机台等级。

### 必须修清的同步边界

现实现使用“上次原始总量”做差，在历史文件减少后再恢复时可能重新奖励已结算区间。V2 要把显示累计值、源观测值、已结算高水位分开：相同项目累计区间只结算一次。

三个值严格分开：`observedTotal` 是本次源报告；`growthTotal` 是永久成长累计；`creditedHighWater` 是已结算的累计边界。同一累计源下，每次合法快照更新：

```text
growthTotal' = max(growthTotal, observedTotal)
delta = max(0, observedTotal - creditedHighWater)
creditedHighWater' = max(creditedHighWater, observedTotal)  // 仅在交易成功提交后
全局成长累计 = Σ(所有持久化项目的 growthTotal)
```

项目从快照消失时只标记当前未观测到，保留该项目、growthTotal、creditedHighWater 和引用；不可用“本次快照项目之和”把全局成长清零。

| 源报告 | 永久成长累计 | 本次可奖励原始新增量 | 已结算高水位 | 机台/伙伴/章节资格 |
| ---: | ---: | ---: | ---: | --- |
| 100K | 100K | 100K | 100K | 正常达成 |
| 40K | 100K | 0 | 100K | 保持 |
| 100K | 100K | 0 | 100K | 保持 |
| 120K | 120K | 20K | 120K | 只推进新增部分 |
| 本次无该项目 | 120K | 0 | 120K | 全部保留 |

默认对同一项目使用持久化已结算高水位。源总量降低不回收金币，也不下调高水位；恢复到旧高水位不铸币，超过之后只奖励超出部分。代价是累计源被重建并重新从零开始时，暂时无法确认其中哪些是真新 token。首版如实提示，保持保守；未来提供稳定事件 ID 的适配器可做事件级去重。不得猜测后发币。

项目 ID 迁移要连同已结算高水位、心爱机台和展示布局引用一起迁移。不可仅迁移机台名称。

领取规则：

- `eligible = lifetimeTokens >= threshold && 未领取该 chapterId`。
- 首次拥有：增加库存一次、记录章节已领取；玩家决定是否摆放或装备。

- 标记领取和发奖为一个存档交易；连点、刷新、动画被跳过、跨标签操作都不能重复。
- 新版本调低门槛：新增符合条件的玩家可领取；已领取不重发。
- 已发布章节奖励不改成其他物品；真要换奖，建立新 chapterId 或明确一次补偿迁移。
- 初次读取旧存档只计算可领取状态，不静默把七个奖励都塞入库存。

## 7. 抽奖、重复与收藏扩建

### 基线概率

普通 54%、非凡 26%、稀有 13%、史诗 6%、传说 1%。先抽稀有度，再在该稀有度目录内按现有逻辑选择。显示时必须区分“某一稀有度的概率”和“某个具体物品的概率”。

十连价格有 10% 折扣；首版不额外保证稀有物。金币不足、非合法抽数、库存配置错误必须在扣费前拒绝。

### 重复补偿

重复不是第二套养成树。星尘只在扭蛋角显示，不占首页 HUD。兑换前显示“120 星尘换 1 件当前图鉴未拥有物，可能包含传说”。所有收藏都拥有时禁用并不扣款；奖池必须排除未知/下架 ID。概率和实际目录以版本锁定，不能随着装饰页面过滤器变化。

### 展示扩建

收集 10 / 25 / 40 / 50 件不同物品时，分别获得霓虹架、展柜照明、陈列地台、纪念冠饰。全部是外观变化，不铸币。

目录扩展后不能把原 50/50 完成纪念撤销。未来主题册具有独立目录范围和完成记录；不以不断增加分母的方式让玩家反复“失去毕业”。

## 8. 常驻确定货架（P2 提案，尚未实现）

从打开商店起可预览全部单品，无日期轮换、无抽签、无额外等级锁。余额足够即可兑换。P1 不做新交易类型，完成后的 P2 用这张单品货架替换容易误解的类型随机购买主入口；旧持有物与价格已成交记录不变，不补扣差价。

| --- | --- | ---: | --- |
| permanent-gg | c_gg | 40 | 简单墙面招牌，早期可攒到的确定小目标 |
| permanent-shelf | u_shelf | 80 | 想要陈列角的人选择书架，约三次单抽的预算 |
| permanent-stool | r_stool | 120 | 机台旁的凳子，比连续抽盲盒更有目的 |
| permanent-palm | r_palm | 180 | 房间绿植焦点，和短期抽取形成取舍 |

已有该物品时显示“已拥有”，不可重复购买、不扣币；首版一件最多展示一份，因此不卖无用途复制品。种类随机商品如果保留在兼容区，文案明确“随机”，且拥有全部同类后禁用；不能冒充上表的确定货架。

此表不增加新物品 ID；新增 offerId 负责价格与购买规则。兑换仍走统一交易。

## 9. 低用量和高用量的体验

下表是单个全新项目首次导入的基础结算示例，不含以后升级倍率；不能宣传为每位用户每天能获得的数量。

| 初次 token | 基础金币 | 能做什么 |
| ---: | ---: | --- |
| 8,000 | 0，余量 8,000 | 第一台数字升级、伙伴回应、免费布置；明确距离首礼和首币 |
| 10,000 | 1 | 第一章植物，第一次可见摆放 |
| 100,000 | 10 | 第二章杯子、小光进化；不要求够抽奖才算有进展 |
| 250,000 | 25 | 至少单抽一次，另有猫礼物 |
| 1,000,000 | 100 | 单抽四次或保留金币，四章可领取 |
| 10,000,000 | 1,000 | 至多四次十连再四次单抽；六章、小光完整进化 |
| 50,000,000 | 5,000 | 内容较快解锁、主题与个性布置成为主要方向 |
| 500,000,000 | 50,000 | 可以大量抽取；须承认有限内容可毕业，不制造新货币无限拖长 |

在大历史用户处，现有商店和 50 件物品不能形成无限期消耗。V2 不承诺无限留存，也不临时提高所有售价；先保证收获演出可跳过、批量操作可靠、毕业纪念完整，再用后续优质主题内容扩展。

## 10. 固定演示脚本

只对**新建演示存档**采用固定脚本，不重置既有演示进度。演示事件经相同结算系统，界面一直显示演示标识。

| 步骤 | 该项目报告的累计 token | 必须发生 |
| --- | ---: | --- |
| 开场 | 0 | 1 个待通电项目位，小光幼体，0 币 |
| 第一次“演示收获” | 10,000 | 至少 1 币、机台数字升级、植物章节可领 |
| 第二次“演示收获” | 100,000 | 蓝色机台进化、小光第二阶段、杯子可领 |
| 第三次“演示收获” | 250,000 | 余额至少 25 币、猫可领、能完成一抽并摆放 |
| 演示后续 | 固定种子的逐步新量 | 多项目、后续进化、零新增量路径可通过专用测试触发 |

演示版本 `cozy-intro-v1`：三个快照只含稳定项目 `demo-first-project`，开场 owned/claims 均空。第一步领植物，第二步领杯子，第三步先领猫；固定演示随机数生成器使用仓库测试同款 `mulberry32`，首抽种子 **22**，在当前目录和稀有度顺序下首奖为 **c_gg（GG 招牌）**。该物品此前没有章节发放，因此一定走“新物品 → 墙面放置”。脚本版本锁定当前目录顺序；目录改变时由测试明确检出并升级脚本，不能静默漂移。

演示用 RNG stream 与真实 RNG 完全隔离，step/RNG 状态在 demo 槽持久化，刷新不重置首抽；只有显式新建演示才重播。UI 明示“演示剧情奖励”，不宣称这一结果代表真实抽奖概率。重复、相框、主题分别使用额外 fixture 验证，不混入第一次完整引导。

P1 六个精修代表样品固定为 `c_sprout`、`c_mug`、`r_cat`、`c_gg`、`r_frame`、`e_sunset`，覆盖地台、伙伴、墙面、肖像、房间。前四件用于主演示，后两件用于装备样板；后两件不因看样板写入真实库存。

固定种子只用于演示与测试，不把真实抽奖写成可预测的剧情结果。首次演示不要直接生成六台相似蓝机器，导致玩家看不见成长过程。

## 11. 调参与验证方法

先验证这四类模拟账户：单项目低用量、多项目中等用量、初次导入 50M、大历史 500M。输入是明确的 token 序列，不用“第几天”充当成长来源。

验证并记录：首币/首礼/首抽阈值、每次导入后的阶段、可领奖励、金币余量、可用兑换入口、重复比例、完成目录的抽数分布。随机结果需至少多个固定种子，报告分位数和样本量，不能只用平均数。

调参优先顺序：先改善低用量的免费互动和确定礼物，其次调整演示节奏，再评估奖励门槛。主转换率和旧存档余额最后才考虑改变，且必须有单独迁移方案。

必须通过的边界：零 token、负数/NaN/无限值源输入、相同报告重放、历史减少再恢复、ID 重命名、跨标签同时领奖、未拥有物耗尽、关闭揭晓动画、旧 v2 存档缺新增字段。程序责任见 [TECHNICAL_DESIGN](TECHNICAL_DESIGN.md)。
